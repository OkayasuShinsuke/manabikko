## 最優先の判断基準（すべてのタスクに適用）

どのタスクをやるときも、最後にこの3つで自己採点してから終わること。
迷ったら、この3つを一番伸ばす選択肢を選ぶ。

1. **面白さ** — 遊んでいて楽しいか（演出・テンポ・驚き）
2. **やりたくなる中毒性** — また開きたくなるか（毎日の理由、コレクション欲、達成感）
3. **知識の定着** — 遊んだ結果、本当に かず・ひらがな が身につくか
   （派手さだけで内容が薄くならないよう注意）

タスク6「面白さの改善」・7「面白さの評価」は独立項目ではなく、
1〜5のどのタスクをやる時も上の3基準で見直す、という運用にする。

## ループの動かし方（重要・2026-09-28に変更）

- **`CronCreate`は使わない。** この環境ではcronジョブが実際には発火しない
  ことが判明した（9時間半アイドルでも1回も発火しなかった）。かわりに
  `ScheduleWakeup`（`/loop`の自己ペース型モードが使う、セッションを直接
  起こす仕組み）を使う。1周の作業が終わって commit・push まで済んだら、
  その周の**最後の行動として** `ScheduleWakeup` を呼び、
  `delaySeconds: 900`（15分、状況により調整可）、
  `prompt: "/loop " + このファイルとADVANCED_APP.mdを読んで両トラックを
  1つずつ進める、という指示文（前回と同内容）` を渡して次の周を予約する。
- **6時間の強制終了は撤廃した（ユーザーの明示的な指示、2026-09-28）。**
  時間による自動停止はしない。
- **唯一の終了条件**: このファイルと `ADVANCED_APP.md` の優先順位リストが
  両方とも全部 [x] になったら、`ScheduleWakeup` を `stop: true` で呼んで
  ループを終了する（新しい周を予約しない）。
- 停止する周は、最後にユーザー向けの短い進捗まとめ（できたこと・残っていること・
  人間の確認が必要な項目）を書いてから止めること。

## エラー時のバックオフ（重要）

サブエージェントの検証で失敗した（pageerrorが出た、Playwrightでの動作確認が
通らない、`git push` が失敗した、など）場合、**そのタスクの変更はcommitしない**
（壊れた状態をリポジトリに残さない）。そのうえで、このファイル（該当トラックが
まなびっこなら本ファイル、上級アプリなら `ADVANCED_APP.md`）の「直近のログ」に

    - ⚠️ ERROR at <date -u の出力>: <何が失敗したか、原因の見立て>

の形で記録する。**次の周に入ったら、まず両ファイルの直近のログの先頭を見る。**
先頭が ⚠️ ERROR で、その時刻から**1時間経っていなければ**、そのトラックは
今回何もしない（サブエージェントを呼ばない、commitしない）でスキップする。
もう片方のトラックにエラーがなければ、そちらは通常どおり進めてよい
（エラーは基本的にトラックごとに個別対応。両方同時にエラーの場合のみ、
その周は実質何もせず次に回す）。1時間経っていれば、同じタスクを再挑戦してよい
（原因を変えずに同じ実装をもう一度依頼するのではなく、前回のエラー内容を踏まえて
一言でも対策を変えてから依頼すること）。

## 「面白さの評価」の扱い方（重要な限界）

ループ自身（Claude）は「楽しいと感じる」ことができないので、次の2つに分ける。

- **客観チェック（ループが自分でできる）**: エラーが出ないか、報酬演出が毎回
  一律すぎないか（音や演出のバリエーション数を数える）、テンポ（1問あたりの
  待ち時間）、操作の分かりやすさ、正答率が異常に低い/高い問題がないか、など。
  これは実際にPlaywrightで操作して確認してよい。
- **人間の試遊が必要（ループはできない）**: 「本当に楽しいか」「また遊びたく
  なるか」は、実際に遊んだ人（ユーザー・お子さん）の感想でしか分からない。
  ループはこれを勝手に採点しない。かわりに、ある程度タスクが進んだ節目で
  「試してほしいポイント」を3〜5個くらいにまとめてユーザーに渡す。

    - 背景: 原因特定済み。`.app { max-width: 560px; margin: 0 auto; }`で
      アプリ全体の幅が560pxに固定されており、Macのブラウザウインドウ等
      大きい画面で開くと、中央に小さく表示されたまま余白が大量に余る。

      16px)なので、画面が大きくてもremベースの要素は一切大きくならない。

    - 方針: スマホでの見た目（既存の390px〜560px幅での段組み・ボタン配置）は
      絶対に崩さないこと。そのうえで、大きい画面（タブレット・PCブラウザの
      大きいウインドウ）で開いたときに、画面サイズに応じてアプリ全体が
      比例して大きく表示されるようにする。
      実装案（実装者の判断でよいが、a)を軸に据えることを推奨）:
      a) `:root`のフォントサイズを`clamp(16px, 最小値 + 画面幅に比例するvw値,
         上限値)`のような可変値にし、remベースの全要素（文字・余白・ボタン
         サイズ）が画面幅に応じて比例拡大するようにする。
      b) `.app`の`max-width: 560px`を、画面が大きいときはもっと広がる値
         （例: `min(94vw, 800px)`程度）に変更する。a)と組み合わせることで、
         widthが広がるのと同時に中身(文字・地図・ボタン)も比例して大きく
         見えるようにする。
      c) 既存の`@media (max-width: 400px)`等の小画面向け調整は維持すること。
    - 制約: 390px幅のスマホでの見た目・レイアウトは変更前と同じに保つこと
      （拡大はあくまで画面が大きいときだけ）。極端に大きい画面(4K等)で
      文字や地図が大きくなりすぎないよう、上限（clamp/minの上限値）は
      常識的な範囲に収めること。
    - 目安: Playwrightで390px(スマホ)・768px(タブレット)・1280px以上(PCの
